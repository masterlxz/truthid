丢失控制您身份的钱包，并不一定意味着丢失身份 — **前提是**您事先配置了监护人。社交恢复完全是可选功能：没有默认的监护人集合，如果从未配置过，`proposeRecovery` 就会直接回滚。本页讲解具体机制；这个取舍的直白版本见[安全模型](/docs/security#what-truthid-does-not-protect-against)。

## 监护人模型

监护人就是一个地址 — 一位朋友的钱包、您自己的另一台设备，或任何您信任的人：能帮您恢复访问权限，但单独一人又无法夺取您身份控制权的人。`configureGuardians(username, guardians[], threshold)` 设置一个 M-of-N 策略：监护人数量上限为 20，阈值可以自由选择（常见推荐是 3-of-5，但链上没有强制这个具体数字）。只有当前控制方可以设置或更改监护人列表，并且在恢复正在进行时无法更改。

## 恢复的生命周期

1. **提议** — 任意一位已配置的监护人调用 `proposeRecovery(username, newController)`，指定应该接管的钱包。
2. **批准** — 每位监护人可以调用一次 `approveRecovery(username)`。提议在获得至少 `threshold` 个批准之前无法推进。
3. **等待时间锁** — 即使达到了阈值，`executeRecovery` 也要等到提议发起 7 天后才能成功。这个窗口期的存在，是为了让真正的控制方 — 如果他们仍然拥有访问权限，而这一切正在他们不知情的情况下发生 — 有时间注意到并取消它。
4. **必要时取消** — *当前*控制方可以在时间锁期间的任何时候调用 `cancelRecovery(username)`，不需要任何监护人参与。这是针对一个协同一致但错误（或恶意）的监护人多数的制衡机制。
5. **执行** — 一旦阈值和时间锁都满足，任何人（不必是监护人）都可以调用 `executeRecovery(username)` 来实际应用这个变更。

`executeRecovery` 会依次做四件事，顺序是刻意安排的 — 先改状态，最后才做外部调用（与合约中其他地方使用的"检查-生效-交互"模式一致，这个模式是在后来的一次安全审查中发现这里存在重入 bug 之后采用的；见[安全模型 → 审计状态](/docs/security#audit-status)）：

1. 在做任何其他事情之前，先把提议标记为已执行，并清空整个监护人配置 — 这样如果被攻陷的旧控制方试图重新进入并在执行过程中发起一个新的 `proposeRecovery`，会立刻失败（`GuardiansNotConfigured`），而不会留下一个存活的第二个提议。
2. 如果旧控制方是一个智能账户（而不是普通钱包），会尝试对它调用 `emergencyWithdraw`，把它的 ETH 余额迁移给新控制方。这是一个 `try`/`catch` — 这一步失败（比如旧控制方不是一个真正的 `TruthIDAccount`，或者新控制方拒绝这笔转账）不会阻止恢复完成；它只会发出一个事件，让卡住的资金在链上可见。
3. 调用 `DeviceRegistry.revokeAllDevices`，让旧控制方曾经授权的每一台设备立刻停止工作 — 否则它们会在身份本该已经易主之后，继续能够创建会话并完成身份验证。
4. 更新 `IdentityRegistry`，让该用户名指向新控制方。

新控制方从**没有配置任何监护人**开始 — 旧的集合被清空，而不是继承下来，这样恢复就不会在没有重新征得同意的情况下，悄悄把同一批人的恢复权力交给新控制方。

## 谁能真正做这件事 — 仅限桌面端 [#who-can-actually-do-this--desktop-only]

配置监护人、发起、批准、执行和取消恢复，都需要一个已连接的钱包直接与 `RecoveryManager` 交互 — 这就是桌面端应用的[监护人管理](/docs/apps/desktop)界面，而且只有桌面端应用可以。移动端应用的监护人界面是**只读**的 — 它会显示当前的监护人列表、阈值，以及任何活跃提议的状态/时间锁倒计时，但每一个真正改变链上状态的操作都必须在桌面端、连接钱包（Ledger 或 WalletConnect）的情况下完成。如果您依赖社交恢复，请确保配置它的人 — 以及可能需要充当监护人的人 — 在关键时刻能够用上桌面端应用。
