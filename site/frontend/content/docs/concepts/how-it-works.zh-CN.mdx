这是对 TruthID 协议端到端的权威讲解。[简介](/docs/intro)和[安全模型](/docs/security)都链接到这里，而不是重复讲一遍。如果您只是想把 TruthID 集成到后端，不需要看这一页 — 去看[快速开始](/docs/quickstart)就够了。如果您想确切了解到底发生了什么，或者正在自己实现一个 TruthID 客户端，请阅读本页。

## 身份创建

身份是一个绑定到控制地址的用户名，记录在 `IdentityRegistry` 中。创建一个身份是一次调用 — `createIdentity(username, controller, v, r, s)` — 但 `(v, r, s)` 并不是可有可无的装饰：它是来自 `controller` 地址自身的签名，证明它确实同意绑定到这个用户名。如果没有这个校验，任何人都可以用别人的地址作为 `controller` 调用 `createIdentity`，从而抢占它 — 包括一个智能账户*即将*要部署到的那个地址，因为 `CREATE2` 地址在部署之前就是可预测的。这个同意签名堵住了这个漏洞：要么是控制方 EOA 直接签名，要么对于一个链上还不存在的智能账户，由它未来的所有者签署一条消息，证明自己控制着未来将拥有它的那把密钥。

用户名被限制为小写字母、数字、`-` 和 `.`，长度 1–64 字节 — 足以排除视觉同形字符伪装，但不追求表达力。

实际操作中，"创建一个身份"就是[智能账户与 Gas](/docs/smart-account)中描述的四步建立流程：签署同意书、创建身份、把智能账户部署到刚刚承诺的地址上、为它注资。所有链上步骤都由所有者钱包支付一次；此后，智能账户就自己养活自己。

## 设备配对 [#device-pairing]

一台设备 — 桌面端应用、移动端应用 — 是一个本地生成的密钥对，其私钥永远不会离开那台设备。把它注册到 `DeviceRegistry` 上是一个两步的**承诺-揭示**过程，而不是一次调用，专门用来防止抢跑：

1. **承诺** — `commitDevice(commitment)`，其中 `commitment = keccak256(devicePubKey ‖ salt ‖ msg.sender)`。这会发布一个哈希，目前还不会透露关于实际设备密钥的任何信息。
2. **揭示** — 在*之后*的一个区块中，`registerDevice(devicePubKey, label, salt, encryptedVaultKey)` 会揭示原像。只有做出原始承诺的地址才能揭示它 — 所以监视内存池等待一笔待处理的 `registerDevice` 交易的人，无法从中复制出设备密钥并抢先注册到自己的身份上，而这正是这个两步方案要防止的攻击。

`encryptedVaultKey` 是可选的 — 如果还没有使用[密码库](/docs/concepts/vault)，可以传空字节。如果存在，它就是密码库的解密密钥，经过 ECIES 加密后专门指向该设备的公钥，使一台新配对的设备无需再次借助所有者钱包即可解密密码库。

一个身份最多可以注册 50 台设备。一台被撤销的设备之后可以重新注册（人们有时会误操作撤销，或者想重新启用一部旧手机）— 但只能由曾经拥有它的同一个身份重新注册；一个曾经属于身份 A 的设备地址，即使在撤销之后，也永远不能成为身份 B 的设备。

## 登录 [#logging-in]

这是中间完全没有服务器的部分。一个想让用户登录的网站：

1. 构建一个 `AuthChallenge`，把它嵌入二维码，并附上它希望已签名响应被 `POST` 回去的 URL：
   ```json
   { "type": "challenge", "nonce": "<uuid>", "issuedAt": 1234567890123, "origin": "https://example.com" }
   ```
2. 用户的手机扫描二维码，向他们展示 `origin`，让他们能准确看到是谁在发起请求，并且 — 如果他们批准 — 用设备密钥（`personal_sign`）在本地对 `JSON.stringify(challenge)` 签名，然后仅通过 HTTPS，把一个 `AuthResponse` 直接 `POST` 到二维码中的 `callbackUrl`：
   ```json
   {
     "approved": true,
     "nonce": "<same uuid>",
     "signature": "0x...",
     "deviceAddress": "0x...",
     "sessionSignature": "0x..."
   }
   ```
3. 网站的后端 — 使用一个 TruthID SDK，从不手动直接与链交互 — 依次验证：(a) `approved` 为真；(b) 挑战尚未过期（默认 30 秒 TTL）；(c) 响应的 `nonce` 与挑战的 `nonce` 一致；(d) 从挑战 JSON 的 `signature` 中恢复出的签名者，恰好就是 `deviceAddress`；(e) `DeviceRegistry.isDeviceActive(deviceAddress)` 在链上为真，即该设备自配对以来没有被撤销；(f) 读取 `getDevice(deviceAddress)` 以获知这台设备属于哪个身份。

这次交换中没有任何环节触碰到 TruthID 运营的服务器 — 挑战活在二维码里，已签名的响应直接从手机发送到接入方自己的后端。

## 会话

登录被批准后，移动端应用 — 不是网站的后端，也不是 SDK — 会单独通过自己的智能账户提交一笔 ERC-4337 `UserOperation`，把会话注册到链上。这是一个刻意的设计：早期版本的 TypeScript SDK 曾经有一个 `registerSession` 方法，但在会话注册变成移动端应用自己完成的事情之后，这个方法就被移除了。

实际存储的内容非常精简：`SessionRegistry.createSession` 接收一个 `hash`（就是 `keccak256(nonce)` — 用链 ID 和 `SessionRegistry` 地址本身做了域分离，所以一次部署产生的会话哈希无法在另一次部署上被重放）、`identityId`、设备的公钥，以及该设备对这个经过域分离的哈希的 ECDSA 签名。合约会校验签名，并确认签名设备确实属于该身份且未被撤销 — 关于这个会话*到底是为了什么*（哪个网站、什么时间）的任何信息都从不会写上链；只有哈希会。哈希所代表的明文内容留在应用的本地存储中。

撤销是对称且低成本的：`revokeSession(hash)` 撤销单个会话，或者 `revokeAllSessions()` — 通过写入一个时间戳，一次 O(1) 调用就撤销到目前为止的所有会话，而不需要遍历每一个会话。

## 背后的签名者

上面提到的每一次链上写入 — 创建身份、注册设备、创建或撤销会话 — 实际上都是由一个 ERC-4337 智能账户执行的，而不是一个普通的 EOA。它识别两级签名者（建立时使用的所有者钱包，以及之后添加的设备，设备被限制永远不能修改账户的控制权归属），并且不涉及任何中继方或 paymaster，自行支付 gas。这个模型，以及完整的建立/注资流程，有自己的一整页：[智能账户与 Gas](/docs/smart-account)。

## 哪些在链上，哪些留在本地

| 公开、链上、永久 | 仅限本地，从不上链 |
|---|---|
| 用户名 ↔ 控制方映射 | 设备私钥 |
| 设备公钥、标签、撤销状态 | 一个会话哈希所代表的原始挑战（`nonce`/`origin`/`issuedAt`） |
| 会话**哈希**（`keccak256(nonce)`，经过域分离） | 密码库内容（单独加密 — 见 [TruthID Vault](/docs/concepts/vault)） |
| 监护人地址、阈值、恢复提议 | 关于您登录过哪个网站，或什么时候登录的任何信息 |
| 密码库 CID/指针（不是内容本身） | 密码库的解密密钥 |

如果您的控制钱包丢失了，上面这些内容都不会因此变得无法恢复 — 这正是社交恢复存在的意义。
