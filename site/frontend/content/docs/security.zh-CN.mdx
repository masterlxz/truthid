TruthID 的安全性建立在由智能合约强制执行的密码学之上，以及永远不离开用户设备的密钥之上 — 而不是建立在对某个服务器的信任之上，因为登录路径中根本没有服务器。本页面是一份坦诚的威胁模型：TruthID 能防护什么，明确不能防护什么，以及当前的审计状态。在决定您对 TruthID 在某个用例中的依赖程度之前，请先阅读本页。

## TruthID 能防护什么

| 威胁 | 机制 |
|---|---|
| 重放攻击（截获的已签名响应被再次使用） | 30 秒的挑战 TTL + 一次性 nonce 追踪，移动端应用和每个 SDK 中的 `verifyAuthResponse` 都会强制执行 |
| 抢先注册设备（攻击者抢先提交别人的设备密钥） | `DeviceRegistry` 使用承诺-揭示方案 — 承诺与 `msg.sender` 绑定，因此只有提交承诺的人才能揭示它 |
| 初始化期间接管 `RecoveryManager` | `setRecoveryManager` 是 `onlyOwner` — 在主网部署前的[人工安全审查](#审计状态)中发现并修复 |
| 登录批准过程中的钓鱼（伪造网站发起登录请求） | 移动端批准界面会在用户批准之前显示发起请求的 `origin` — 伪造网站会显示一个明显不对的不同域名 |
| 传输中的已签名响应被拦截 | 移动端应用拒绝任何不是 `https://` 的 `callbackUrl` — 没有办法让二维码指向一个明文端点 |
| 设备密钥被提取 | 密钥在设备本地生成，并由操作系统凭据存储加密保存 — Android Keystore 支持的存储、iOS 钥匙串、桌面端的操作系统凭据管理器（macOS 钥匙串、Windows 凭据管理器、Linux Secret Service）。它们永远不会离开设备，也永远不会被发送到任何服务器，包括 TruthID 的各个 SDK。（并非专门使用 iOS 安全隔区 — 安全隔区只支持 P-256 曲线，而 TruthID 的设备密钥使用 secp256k1，与以太坊使用的曲线相同。软件加密静态存储仍然是一种真实的防护，例如可以防止另一个应用或一份被盗的未加密备份读取该密钥 — 只是不像安全隔区密钥那样具有硬件级隔离。） |
| 伪造会话创建 | `createSession` 要求设备密钥提供 ECDSA 签名，并与 `DeviceRegistry` 进行交叉校验 — 在[人工安全审查](#审计状态)期间修复，审查发现该函数最初是无权限限制的 |
| 控制钱包丢失，**前提是事先配置了监护人** | M-of-N 社交恢复（阈值最多可达 20 位监护人 — 合约层面没有强制的默认值；3-of-5 是常见的推荐配置），生效前有 7 天时间锁 |
| 恢复后新控制方被重用旧的监护人集合 | `executeRecovery` 会自动清空旧的监护人配置 — 新控制方必须重新选择加入 |
| 通过无上限的监护人列表进行 gas 消耗攻击 | `RecoveryManager` 将监护人数量上限设为 20 |
| 用户名视觉伪装（同形字符） | 用户名被限制为 ASCII 字母、数字、`-` 和 `.` |

## TruthID 不能防护什么 [#what-truthid-does-not-protect-against]

<Callout title="没有配置监护人就永远无法恢复" type="error">
除非身份的控制方事先明确设置了监护人，否则 `proposeRecovery` 会以 `GuardiansNotConfigured` 回滚。没有其他恢复途径 — 在没有配置监护人的情况下丢失控制钱包，意味着该身份将**永久**无法访问。这是一个刻意的取舍（没有后门，没有管理员越权），但这也意味着恢复是可选功能，而不是自动生效的。
</Callout>

- **已被入侵、已解锁的设备。** 如果恶意软件或攻击者控制了一部已经解锁的手机或桌面设备，他们可以像合法用户一样批准登录。这与所有基于设备的双因素方案面临的局限是一样的 — TruthID 保护的是存储中的密钥，而不是正在使用中的设备。
- **不受信任的 RPC 端点。** 每个 SDK 都是从一个 RPC 地址读取设备和会话状态（`isDeviceActive`、会话哈希）— 默认是一个公共节点，或者由接入方自行配置。客户端没有任何密码学手段能证明该 RPC 说的是真话；一个恶意或被入侵的 RPC 可能会谎称一台已被撤销的设备仍处于活跃状态。对于高价值登录流程的接入方，建议自行运行节点，或选择一个信任的 RPC 提供商。
- **第三方专业审计。** 这些合约目前只经过了内部人工审查（见下方[审计状态](#审计状态)）— 尚未有外部机构对这份代码进行过审计。请将其视为早期阶段的软件。
- **部署后发现的 bug。** TruthID 的所有合约都没有部署在升级代理之后，这是刻意的设计 — 一个 bug 无法在已部署的字节码中被热修复。*可以*改变的是一个应用指向哪一次部署：`TruthIDAccount` 和 `TruthIDAccountFactory` 都有一个由所有者控制的 `updateRegistries` 函数，专门用于在项目迁移到一套全新合约之后，把已有的智能账户重新指向新地址 — 就像上面提到的重入问题被发现并修复后那样，这种情况已经发生过不止一次。所以这里的"不可变"指的是没有静默升级，而不是说已部署的地址永远固定不变 — 当前地址见[智能合约](/docs/contracts)，迁移实际是如何发生的见 [TruthID 工作原理](/docs/concepts/how-it-works)。
- **接入方自己的后端。** 限制挑战创建的速率、保护密钥等敏感信息，以及一般的服务器加固，都是接入方自己的责任 — TruthID 的 SDK 只验证签名和一次链上读取，仅此而已。
- **被说服去批准一个真实请求的用户。** 手机会显示发起请求方真实的 `origin`，但点击"批准"仍然是一个人做出的决定。被巧妙的话术欺骗（或者只是没有读屏幕内容）的人，仍然可能批准一次本不该批准的登录 — 这是所有基于批准的双因素方案都存在的同样的残余风险。

## 范围：本页讲的是登录 TruthID 本身，而不是密码库 [#scope-this-page-is-about-logging-into-truthid-not-the-vault]

TruthID Vault（桌面端和移动端应用中的可选密码管理器模块）可以生成 TOTP 验证码，也可以作为 WebAuthn/通行密钥认证器 — 但这些是用来登录您已经把凭据保存在密码库里的*其他*服务，而不是用来登录 TruthID 本身。TruthID 本身从不要求密码、TOTP 验证码或通行密钥 — 设备密钥的持有加上上面描述的批准流程，就是登录机制的全部。密码库自身的威胁模型（密码库密钥推导、备份加密、按设备的权限）见 [TruthID Vault](/docs/concepts/vault)。

## 桌面端:密钥存放在哪里 [#desktop-where-secrets-live]

桌面应用将其私钥(设备密钥、密码库密钥、本地钱包、Arweave 钱包)保存在操作系统密钥环中:Windows 上是凭据管理器,Linux 上是 Secret Service。在 Windows 上,它由 DPAPI 保护,该机制将密钥绑定到当前登录的用户账户。**它并不存放在 TPM 中**——之前 README 中这样的说法并不准确。

如果操作系统密钥环不可用(受限或无界面的会话、损坏的 Secret Service 守护进程),应用会退回到 `~/.truthid`(Windows 为 `%USERPROFILE%\.truthid`:`device.key`、`vault.key`、`local_wallet.key`、`arweave_wallet.json`)下的普通未加密文件。在 Linux 上这些文件以 `0600` 权限创建;在 Windows 上应用不设置 ACL,因此它们继承所在文件夹的权限。任何能读取该文件夹的人都能读取它们。

应用不再悄悄这样做:只要存在这些文件中的任何一个,仪表盘和设置页都会显示警告。修复密钥环并重启应用,即可不再依赖这一后备方案。可选的应用锁(设置)会在打开应用时增加密码提示,但不会加密后备文件。

## 桌面端:本地签名服务 [#desktop-the-local-signer-service]

运行时,桌面应用监听 `127.0.0.1`(仅回环——绝不是网络接口),以便浏览器扩展和第三方应用可以请求它签名、固定(pin)内容、编辑密码库或自动填充。有两个重要特性:

- **每一个会签名、修改密码库、发布内容或泄露已存密钥的操作,都会被挂起,直到你在应用中做出决定。** `sign-request`、`sign-message`、`pin`、`vault-edit`、`autofill-address` 和 `autofill-creditcard` 各自会弹出一个审批对话框;没有你的决定,HTTP 调用会超时,什么也不会发生。已批准的自动填充只能返回对话框所提供的候选项之一。`vault-edit` 还要求发起请求的设备在密码库中拥有写权限。仅凭一个 HTTP 请求永远无法完成其中任何一项。
- **跨源访问是有意开放的。** 该服务响应任何浏览器源(宽松的 CORS),因为扩展的内容脚本是从页面所在的源调用它的。这些端点没有单独的身份验证,因此任何本地进程——或任何网页,只要它能找到端口——都可以*发起请求*。它能得到什么,受上述审批对话框的限制。有两件事无需批准即可得知:服务正在运行(`ping`),以及密码库中是否保存有任何支付卡或地址("未保存"的回答)。

桌面 webview 在内容安全策略(CSP)下运行,UI 的文件访问仅限于你在原生打开/保存对话框中选择的文件。

## 审计状态 [#audit-status]

这些合约已经经过两轮人工安全审查（未使用 Slither 或 Mythril 之类的自动化工具）：访问控制、重入、抢跑、时间戳依赖、拒绝服务，以及输入校验。

- **主网上线之前**，一次初步审查发现了 7 个问题，其中包括一个严重 bug（`setRecoveryManager` 没有权限保护 — 与 2017 年 Parity 多签黑客事件属于同一类 bug）。这 7 个问题在部署前全部修复。
- **在后续开发过程中**，对 `contracts/` 目录的一次跟进审查在 `RecoveryManager.executeRecovery` 中发现了一个严重的重入 bug：一个已经攻陷旧控制方的攻击者，可以在 `emergencyWithdraw` 转出资金的过程中重新进入 `proposeRecovery`，从而在恢复过程中劫持该身份。修复方式是将 `executeRecovery` 重新排序为"检查-生效-交互"（Checks-Effects-Interactions）模式 — 状态在任何外部调用发生之前就已经最终确定，而不是依赖 `ReentrancyGuard`。这与最初 `setRecoveryManager` 那次发现所用的修复模式相同。

这样的审查在整个开发过程中定期进行，而不只是在上线前做一次 — 项目自身的贡献指南要求每个主要模块（合约、桌面端、移动端、SDK）在每次发布前都要经过一轮审查。这个项目**尚未**经过第三方专业审计。

如果您发现了漏洞，请通过仓库的 [GitHub Security 标签页](https://github.com/masterlxz/truthid/security)私下报告，而不要公开提交 issue。
